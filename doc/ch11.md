# Chapitre 11 — Écrire des tests automatisés

## Objectif du chapitre

Ce chapitre montre comment Rust intègre les tests directement dans l'outillage standard : un **framework de test** avec l'attribut `#[test]`, des **macros d'assertion** (`assert!`, `assert_eq!`, `assert_ne!`), et la commande `cargo test` qui exécute les tests en parallèle. Il couvre la façon de **contrôler l'exécution** des tests (filtrage, threads, sortie, tests ignorés), puis l'**organisation** des tests en tests unitaires (dans les fichiers sources) et tests d'intégration (dans le dossier `tests/`).

## Concepts abordés

### 1. L'anatomie d'une fonction de test

- **Définition** : une fonction de test est une fonction Rust classique, précédée de l'attribut `#[test]`. Rust la compile comme un test et l'exécute séparément. Pour bien tester, on écrit au moins deux fonctions : une qui vérifie le comportement attendu (ex. `add`), une qui vérifie le cas d'échec (ex. `add_three` qui renvoie le mauvais résultat).
- **Pourquoi elle existe** : le compilateur ne détecte que les erreurs de syntaxe et de types ; il ne peut pas savoir si un comportement est *logiquement* correct. Les tests transforment une intention (« `add(2,2)` doit donner `4` ») en code vérifiable.
- **Structure** : on utilise `assert!` pour vérifier une condition. Si elle est vraie (`true`), le test passe ; sinon, la macro appelle `panic!` et le test échoue.
- **À retenir** : un test échoue **uniquement** s'il panique. Une fonction de test qui se termine normalement passe, même si elle ne vérifie rien.

### 2. Les macros d'assertion et les messages personnalisés

- **`assert!(condition)`** : vérifie qu'une condition est `true` ; échoue (panique) sinon. Utilisée quand la condition décrit entièrement le succès.
- **`assert_eq!(a, b)`** : vérifie que deux valeurs sont **égales** (`==`). Échoue en affichant les deux valeurs, ce qui aide au débogage. Le succès est décrit par l'*égalité* de deux valeurs, l'échec par leur différence.
- **`assert_ne!(a, b)`** : vérifie que deux valeurs sont **différentes**. Utile quand on veut garantir que le code ne produit pas une valeur précise, ou qu'un `if` à deux branches fonctionne dans chaque direction.
- **Messages personnalisés** : toutes ces macros acceptent un message en second argument (`assert!(a, "message personnalisé")`), formaté comme `println!` avec `{}`. Si l'assertion échoue, le message s'affiche. Pratique pour préciser *quel* invariant n'est pas respecté.
- **Condition préalable** : `assert_eq!` et `assert_ne!` exigent que les valeurs implémentent `PartialEq` (comparaison) **et** `Debug` (affichage en cas d'échec). C'est pourquoi on ajoute souvent `#[derive(Debug, PartialEq)]` sur ses propres types.
- **À retenir** : `assert!` n'affiche **rien** du programme ni des valeurs comparées en cas d'échec (juste une ligne « assertion failed »). Si on a besoin de voir les valeurs, `assert_eq!`/`assert_ne!` sont plus adaptés.

### 3. Vérifier les paniques avec `#[should_panic]`

- **Définition** : l'attribut `#[should_panic]` inverse la logique : le test **réussit** si le code panique, et **échoue** s'il se termine normalement. Il sert à tester les chemins d'erreur, par exemple « un index hors limites doit paniquer ».
- **Pourquoi il existe** : certains comportements sont *intentionnellement* des erreurs (garde d'un constructeur qui refuse un guess hors de l'intervalle 1..=100). On veut vérifier que l'erreur se produit bien.
- **Précision du message** : avec `#[should_panic(expected = "message attendu")]`, on peut vérifier que la panique correspond au **bon message**. Si la panique arrive avec un autre message, le test échoue — même si quelque chose panique.
- **Limite** : l'attribut ne distingue **pas** d'où vient la panique : une panique provenant d'un autre endroit du test (bug du test lui-même) ferait quand même réussir le test. On le vérifie avec le message attendu.
- **À retenir** : c'est le complément d'`assert!` : `assert!`/`assert_eq!` vérifient que le code *ne panique pas*, `should_panic` vérifie qu'il *panique au bon endroit*.

### 4. Les tests avec `Result<T, E>`

- **Définition** : une fonction de test peut renvoyer `Result<(), E>` au lieu de rien. Le test passe si elle renvoie `Ok(())`, échoue si elle renvoie `Err(quelque chose)`.
- **Pourquoi il existe** : cela permet d'utiliser l'opérateur `?` dans un test : remonter une erreur la fait échouer sans écrire de `assert!` ni de `match`.
- **Syntaxe** : `fn test() -> Result<(), String> { ... Ok(()) }`. Le type d'erreur doit implémenter `Debug` pour être affiché.
- **Restriction importante** : on ne peut **pas** combiner `#[should_panic]` avec une fonction qui renvoie `Result<T, E>`. Pour tester une panique dans un test à `Result`, il faut soit la transformer en `Err`, soit utiliser une autre approche.
- **À retenir** : `?` dans un test renvoie une `Err` prématurément — c'est la façon idiomatique de faire échouer un test sur une erreur.

### 5. Contrôler l'exécution des tests

- **Exécution en parallèle** : par défaut, `cargo test` lance les tests **en parallèle sur plusieurs threads** pour aller plus vite. Les tests doivent donc être **indépendants** : ils ne doivent pas dépendre d'un état partagé (fichier, variable globale, temps) qui changerait selon l'ordre ou la concurrence.
- **`-- --test-threads=1`** : tout ce qui suit `--` est passé au binaire de test. `--test-threads=1` force l'exécution en un seul thread, séquentielle. À utiliser quand les tests partagent de l'état et interfèrent entre eux.
- **`-- --show-output`** : par défaut, les `println!` des tests *qui passent* ne s'affichent pas (ils sont capturés) ; seuls ceux des tests qui échouent apparaissent. `--show-output` force l'affichage de toutes les sorties.
- **Filtrer par nom** : on peut passer une chaîne au binaire (`cargo test add`). Seuls les tests dont le **nom contient** la chaîne s'exécutent. Cela permet de lancer un sous-ensemble : un seul test, ou tous ceux qui contiennent « add ».
- **`#[ignore]`** : l'attribut marque un test à ne pas exécuter par défaut (il s'affiche comme « ignored »). Utile pour les tests coûteux ou longs. On les lance avec `cargo test -- --ignored`.
- **À retenir** : le séparateur `--` est la frontière entre les arguments de `cargo test` (à gauche) et ceux du **binaire de test** (à droite).

### 6. L'organisation : tests unitaires vs tests d'intégration

- **Définition** : Rust distingue deux familles. Les **unit tests** vivent dans les fichiers sources (`src/lib.rs`), à côté du code, dans un module `mod tests` avec `#[cfg(test)]`. Les **integration tests** vivent dans le dossier `tests/`, chaque fichier étant un **crate séparé** qui importe le code public de la bibliothèque.
- **Pourquoi les distinguer** : les unit tests testent chaque unité de code **en interne** (avec accès aux éléments privés), les integration tests testent le code **comme un utilisateur externe** : uniquement l'interface publique (`pub`), en l'important avec `use`. On teste ainsi que les pièces fonctionnent *ensemble*, pas seulement séparément.
- **`#[cfg(test)]`** : cet attribut fait que le module de tests n'est compilé **que** pendant `cargo test`, jamais dans le binaire de production. Le binaire livré n'embarque donc aucun code de test.
- **Sous-module de test** : le module `tests` s'écrit `#[cfg(test)] mod tests { ... use super::*; ... }` — `use super::*` importe le code du module parent (la crate), car le module de test est un **module enfant**.
- **Fichiers d'intégration** : chaque fichier de `tests/` est une crate indépendante. On y met `use mon_crate::fonction;` pour accéder à l'API publique. `cargo test` affiche une ligne par fichier d'intégration (ex. `tests/integration_test.rs`).
- **Dossier partagé** : pour factoriser un code de mise en place commun à plusieurs fichiers d'intégration, on crée `tests/common/mod.rs` (et non `tests/common.rs`). Un sous-dossier empêche que `common` soit traité comme un fichier de test ; on y accède avec `mod common;`.
- **Crées binaires** : les tests d'intégration ne fonctionnent que pour les **library crates**. Un projet uniquement binaire (`src/main.rs` sans `src/lib.rs`) ne peut pas être testé en intégration directement : il n'expose pas d'API à importer. Solution : garder la logique dans `src/lib.rs` et laisser `main.rs` être une fine coquille qui l'appelle.
- **À retenir** : unit = *interne, privé, côté code* ; intégration = *externe, public, côté `tests/`*.

## Nouveaux mots-clés

| Mot-clé / attribut | Utilisation |
|---|---|
| `#[test]` | Marque une fonction comme test exécutable par `cargo test` |
| `cargo test` | Compile et exécute les tests (binaire de test) |
| `assert!` | Macro d'assertion : échoue si la condition est `false` |
| `assert_eq!` | Vérifie l'égalité de deux valeurs (`==`) |
| `assert_ne!` | Vérifie la différence de deux valeurs (`!=`) |
| `#[should_panic]` | Le test réussit seulement si le code panique |
| `expected` | Paramètre de `#[should_panic]` pour exiger un message précis |
| `Result<T, E>` en test | Un test peut renvoyer `Ok(())`/`Err` et utiliser `?` |
| `#[cfg(test)]` | Ne compile le module de tests que pendant `cargo test` |
| `mod tests` | Module conventionnel contenant les tests unitaires |
| `use super::*` | Importer le code parent dans le module de tests |
| `tests/` | Dossier des tests d'intégration (crates séparés) |
| `#[ignore]` | Test à ne pas lancer par défaut |
| `--test-threads` | Nombre de threads d'exécution des tests |
| `--show-output` | Afficher les sorties des tests qui passent |
| `--ignored` | Lancer uniquement les tests ignorés |
| `tests/common/mod.rs` | Sous-module partagé non traité comme fichier de test |
| unit test / integration test | Test interne (privé) vs test externe (public) |

## Fonctions, méthodes et macros importantes

| Fonction / Macro | Description |
|---|---|
| `assert!(condition)` | Panique si la condition est fausse |
| `assert_eq!(gauche, droit)` | Panique si les deux valeurs sont différentes (affiche les deux) |
| `assert_ne!(gauche, droit)` | Panique si les deux valeurs sont égales |
| `assert!(cond, "message {}", var)` | Assertion avec message personnalisé (comme `println!`) |
| `#[should_panic(expected = "…")]` | Test qui doit paniquer avec le message donné |
| `fn test() -> Result<(), String>` | Test à `Result`, échoue sur `Err`, autorise `?` |
| `cargo test` | Lance tous les tests de tous les crates |
| `cargo test nom` | Lance les tests dont le nom contient `nom` |
| `cargo test -- --test-threads=1` | Exécution séquentielle (un thread) |
| `cargo test -- --show-output` | Affiche les `println!` des tests qui passent |
| `cargo test -- --ignored` | Lance les tests marqués `#[ignore]` |

Le fil conducteur : d'abord **comment vérifier** (macros d'assertion, paniques attendues, `Result`) ; ensuite **comment lancer** (`cargo test` et ses options de contrôle) ; enfin **où écrire** les tests (unitaires côté code privé, d'intégration côté interface publique).

## Pièges classiques

1. **Écrire une fonction de test sans `#[test]`** — sans l'attribut, `cargo test` ne l'exécute pas ; elle est juste une fonction normale jamais appelée.
2. **Un test qui ne vérifie rien** — un test passe s'il ne panique pas. Oublier d'appeler `assert!`/`assert_eq!` donne un test qui « réussit » sans tester quoi que ce soit.
3. **Utiliser `assert!` là où `assert_eq!` serait utile** — en cas d'échec, `assert!` n'affiche pas les valeurs comparées, ce qui complique le débogage.
4. **Oublier `PartialEq`/`Debug`** — `assert_eq!` sur un type personnalisé sans `#[derive(PartialEq, Debug)]` ne compile pas.
5. **Tester une panique avec `#[should_panic]` trop large** — une panique venue d'ailleurs ferait passer le test ; utiliser `expected` pour cibler le message.
6. **Combiner `#[should_panic]` et un test qui renvoie `Result`** — interdit par le langage : il faut choisir l'un ou l'autre.
7. **Des tests dépendants d'un état partagé** — par défaut ils tournent en parallèle ; l'ordre et la concurrence faussent les résultats. Utiliser `--test-threads=1` ou rendre les tests indépendants.
8. **Confondre l'argument de `cargo test` et du binaire** — tout ce qui est après `--` concerne le binaire de test (`--test-threads`, `--ignored`, …), pas `cargo` lui-même.
9. **Créer `tests/common.rs` au lieu de `tests/common/mod.rs`** — `common.rs` serait traité comme un fichier de test (ligne « running X tests » en trop) ; le sous-module dans un dossier l'évite.
10. **Vouloir tester un binaire en intégration** — sans `src/lib.rs`, aucune API publique à importer depuis `tests/`. Mettre la logique dans une library crate.

## Résumé

1. **Une fonction de test** = fonction normale marquée `#[test]` ; elle échoue seulement si elle panique.
2. **`assert!`** vérifie une condition ; **`assert_eq!`/`assert_ne!`** comparent deux valeurs et affichent les deux en cas d'échec (exigent `PartialEq` + `Debug`).
3. **Les messages personnalisés** en second argument précisent l'invariant qui a échoué.
4. **`#[should_panic(expected = "…")]`** vérifie qu'une panique *prévue* se produit, au bon message.
5. **Les tests peuvent renvoyer `Result<(), E>`** pour utiliser `?`, mais ne se combinent pas avec `#[should_panic]`.
6. **`cargo test`** exécute en parallèle par défaut ; on contrôle avec `--test-threads=1`, `--show-output`, le filtrage par nom et `--ignored`.
7. **`#[cfg(test)]`** : les unit tests ne sont compilés que pendant `cargo test`, jamais en production.
8. **Unit tests** (module `tests` dans `src/`, `use super::*`) testent l'intérieur privé ; **integration tests** (`tests/`) testent l'interface publique comme un utilisateur.
9. **`tests/common/mod.rs`** factorise un code commun sans être compilé comme un test.
10. **Seules les library crates** sont testables en intégration : le code principal va dans `src/lib.rs`, `main.rs` reste une coquille.
