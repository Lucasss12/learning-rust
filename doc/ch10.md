# Chapitre 10 — Les types génériques, les traits et les lifetimes

## Objectif du chapitre

Ce chapitre présente les trois outils qui permettent d'écrire du code **réutilisable** et **sans duplication** tout en restant sûr :
1. les **types génériques** (`generic types`) pour écrire une seule version d'une fonction, d'une structure ou d'une énumération qui fonctionne avec plusieurs types ;
2. les **traits** pour définir un comportement partagé et abstraire ce qu'un type sait faire, indépendamment de son type concret ;
3. les **lifetimes** pour garantir que chaque **référence** utilisée pointe vers une donnée encore vivante, en évitant les références invalides (dangling references).

Le chapitre se termine en combinant les trois dans une même signature de fonction.

## Concepts abordés

### 1. Les types génériques (generic types)

- **Définition** : un type générique remplace un type inconnu par un paramètre de type, écrit entre chevrons (`<T>`). La fonction, la struct ou l'enum est alors écrite **une seule fois** et s'adapte au type réel à l'utilisation.
- **Pourquoi ils existent** : sans eux, il faudrait dupliquer le code pour chaque type (une fonction `largest_i32` et une `largest_char` identiques). Le générique supprime cette duplication.
- **Où on les trouve** : en paramètre de **fonction** (`fn largest<T>(list: &[T]) -> T`), dans les **structs** (`struct Point<T> { x: T, y: T }`), les **enums** (`Option<T>`, `Result<T, E>` vus précédemment) et les **méthodes** (`impl<T> Point<T> { fn x(&self) -> &T }`).
- **Erreurs fréquentes** : écrire une définition générique mais oublier de préciser le type à l'utilisation (le compilateur demande une annotation) ; déclarer `impl Point<T>` au lieu de `impl<T> Point<T>`.
- **À retenir** : le générique ne coûte **aucune performance à l'exécution**. Rust fait de la **monomorphisation** : il compile une copie concrète du code pour chaque type utilisé. Le code est plus lisible à la compilation, identique à la main à l'exécution.

### 2. Les traits

- **Définition** : un trait est une collection de **méthodes** qu'un type doit implémenter pour satisfaire un comportement donné. Il définit *ce qu'un type sait faire*, pas *ce qu'il est*.
- **Pourquoi ils existent** : pour regrouper des comportements communs à plusieurs types (afficher, trier, résumer...) et écrire du code qui fonctionne sur **tout type qui implémente ce trait**, sans connaître le type précis.
- **Déclaration** : `trait Summary { fn summarize(&self) -> String; }` — la signature seule, sans corps.
- **Implémentation** : `impl Summary for NewsArticle { ... }` fournit le corps des méthodes. Un type peut implémenter autant de traits qu'il veut.
- **Implémentations par défaut** : une méthode peut avoir un **corps par défaut** dans la définition du trait ; un type peut l'utiliser tel quel ou la surcharger.
- **Erreurs fréquentes** : implémenter un **trait externe** sur un **type externe** (ni l'un ni l'autre n'est défini dans notre crate) — c'est interdit par la **orphan rule** : on ne peut implémenter un trait que si le trait ou le type appartient à notre crate.
- **À retenir** : les traits sont l'équivalent des **interfaces**, mais en les *implémentant*, on n'hérite de rien : on déclare les méthodes soi-même. Un type est ce qu'il est ; ses traits décrivent ses capacités.

### 3. Les trait bounds et `impl Trait`

- **Définition** : un **trait bound** est une contrainte qui dit « ce paramètre générique doit implémenter tel trait ». Sans contrainte, on ne peut pas appeler de méthode du trait sur une valeur générique (le compilateur refuse).
- **Pourquoi ils existent** : un générique tout seul ne donne **aucun accès** aux méthodes. Le trait bound dit au compilateur : *ce type sait faire ça*, donc on peut l'utiliser.
- **Syntaxes** :
  - après le paramètre : `fn largest<T: PartialOrd + Copy>(list: &[T]) -> T` ;
  - paramètre direct : `fn notify(item: &impl Summary)` — sucre syntaxique du cas précédent ;
  - plusieurs contraintes avec `+` : `fn notify(item: &(impl Summary + Display))` ;
  - clause `where` pour alléger les signatures complexes : `fn some<T, U>(t: &T, u: &U) where T: Display + Clone, U: Clone + Debug`.
- **Retour de fonction** : on peut renvoyer un `impl Trait` (`fn returns_summarizable() -> impl Summary`), ce qui est pratique pour les **closures et itérateurs**. Attention : la fonction doit alors renvoyer **un seul type concret**.
- **Application à l'exemple `largest`** : comparer avec `>` exige que `T` implémente `PartialOrd` ; renvoyer l'élément par valeur exige que `T` soit `Copy` (ou sinon `Clone`). Sans ces bounds, le compilateur refuse.
- **Implémentation conditionnelle** : on peut définir des méthodes uniquement pour certains types (`impl<T: Display + PartialOrd> Pair<T>`), et Rust applique des **implémentations de traits « blanket »** (ex. `ToString` est automatiquement implémenté pour tout type implémentant `Display`).
- **Erreurs fréquentes** : oublier un bound et ne pas comprendre pourquoi le compilateur refuse d'appeler une méthode ; renvoyer `impl Trait` en croyant pouvoir renvoyer des types différents selon les cas.
- **À retenir** : le trait bound est le pont entre le générique et les méthodes : *générique = quel type ?* + *bound = quelles capacités ?*

### 4. Les lifetimes

- **Définition** : une lifetime décrit la **durée de validité** d'une référence, c'est-à-dire la région du code pendant laquelle la donnée référencée est garantie vivante. C'est un concept **à la compilation**, sans coût à l'exécution.
- **Pourquoi elles existent** : pour empêcher les **dangling references** — une référence vers une donnée déjà libérée. Sans elles, on pourrait utiliser une référence après la mort de sa donnée (le programme planterait ou corromprait la mémoire).
- **Le borrow checker** : le vérificateur d'emprunts compare les lifetimes des références et refuse tout programme où une référence risque d'outrepasser la donnée qu'elle désigne.
- **Annotations** : elles utilisent une apostrophe (`'a`), se déclarent avec le générique (`<'a>`) et **relient les références entre elles** : `fn plus_long<'a>(x: &'a str, y: &'a str) -> &'a str` signifie « les entrées et la sortie ont la même durée de vie commune ». Elles ne changent pas la durée de vie réelle des données ; elles la *décrivent*.
- **Structures** : une struct peut contenir une référence, mais doit alors déclarer sa lifetime : `struct Extraits<'a> { partie: &'a str }`.
- **Les règles d'élision** : le compilateur applique 3 règles automatiques pour *inférer* les lifetimes quand il n'y a pas d'ambiguïté. Si une signature a plusieurs références en entrée, l'annotation devient nécessaire.
- **Méthodes** : pour une struct à lifetime, on écrit `impl<'a> Extraits<'a> { ... }` ; la 3ᵉ règle d'élision attribue la lifetime de `&self` au résultat quand une méthode prend `&self`.
- **`'static`** : une lifetime particulière qui vit **toute la durée du programme** (ex. les chaînes littérales `"..."`). Il ne faut l'exiger que si la donnée vit vraiment pour toujours.
- **Erreurs fréquentes** : vouloir retourner une référence vers une variable **locale** de la fonction (dangling reference — le compilateur refuse) ; annoter une lifetime là où elle n'apporte rien ; surutiliser `'static` ; croire que les annotations *prolongent* la vie des données.
- **À retenir** : le but n'est pas de « faire plaisir » au compilateur, mais de **prouver la sûreté** : le code doit être vrai — une référence retournée doit toujours pointer vers une donnée qui vit plus longtemps que son usage.

### 5. Génériques, traits et lifetimes réunis

- **Définition** : les trois peuvent apparaître dans une seule fonction : `fn plus_long<'a, T>(x: &'a T, y: &'a T) -> &'a T where T: Display { ... }`.
- **Ordre dans la signature** : les paramètres de lifetime d'abord, puis les paramètres de type, puis les paramètres de valeur (`<'a, T>`).
- **Pourquoi les combiner** : on veut à la fois une durée de validité partagée (`'a`), une flexibilité de type (`T`) et des capacités garanties (bound `Display`).
- **À retenir** : les trois mécanismes répondent à trois questions différentes — *combien de temps vit la référence ?*, *sur quel type ?*, *avec quelles capacités ?* — et s'empilent naturellement.

## Nouveaux mots-clés

| Mot-clé / type | Utilisation |
|---|---|
| `<T>` | Paramètre de type générique (fonction, struct, enum, méthode) |
| `monomorphisation` | Compilation d'un générique en types concrets (aucun coût à l'exécution) |
| `trait` | Collection de méthodes définissant un comportement partagé |
| `impl Trait for Type` | Implémenter un trait pour un type |
| trait bound | Contrainte : le type générique doit implémenter le trait |
| `impl Trait` | Paramètre ou retour « un type qui implémente ce trait » |
| `+` | Combiner plusieurs trait bounds (`T: Display + Clone`) |
| `where` | Clause pour alléger une longue liste de trait bounds |
| orphan rule | Interdiction d'implémenter un trait externe sur un type externe |
| `PartialOrd` | Trait des comparaisons avec `>`, `<`, `>=`, `<=` |
| `Copy` / `Clone` | Traits de duplication (par bit ou par méthode) |
| `Display` | Trait d'affichage lisible (`{}`) |
| `ToString` | Trait fourni automatiquement à tout type implémentant `Display` |
| lifetime `'a` | Région de validité d'une référence (annotée par une apostrophe) |
| `<'a>` | Déclaration d'un paramètre de lifetime générique |
| borrow checker | Vérificateur d'emprunts qui valide les lifetimes |
| dangling reference | Référence vers une donnée déjà libérée (interdite) |
| lifetime elision | Règles automatiques d'inférence des lifetimes |
| `'static` | Lifetime valable toute la durée du programme |

## Schéma mental

```
            CODE DUPLIQUÉ ?
                 │
    ┌────────────┴────────────┐
    │                         │
 Types génériques          Traits
 (réutiliser un type)      (réutiliser un comportement)
    │                         │
  <T>                    trait Summary { ... }
    │                         │
  fn / struct / enum      impl Summary for Type
  / méthodes                  │
    │                    ┌────┴────┐
    │             impl Summary    &impl Summary
    │             (paramètre)     (paramètre)
    │                    └────┬────┘
    │                    trait bounds
    │                  (contraintes de capacités)
    │                         │
    │              générique + bound = méthode utilisable
    │                         │
    └────────────┬────────────┘
                 │
              lifetimes
    (garantir que les références restent valides)
                 │
        fn plus_long<'a>(x: &'a str, y: &'a str) -> &'a str
        struct Extraits<'a> { partie: &'a str }
                 │
    ┌────────────┴────────────┐
    │                         │
 borrow checker         elision ('a, 'static)
 (valide)               (infère les règles 1-2-3)
                 │
    TOUT RÉUNI : fn plus_long<'a, T>(x: &'a T, y: &'a T) -> &'a T
                 where T: Display
```

Le fil conducteur : le **générique** répond à « *sur quel(s) type(s) ?* », le **trait / trait bound** répond à « *avec quelles capacités ?* », la **lifetime** répond à « *pendant combien de temps est-ce valide ?* ». On choisit les deux premiers pour **factoriser** le code ; la troisième, imposée par le borrow checker, pour **prouver la sûreté** des références. Un trait bound ne sert qu'à *autoriser* un appel de méthode sur un générique ; une annotation de lifetime ne fait que *décrire* une relation entre références déjà vraie.

## Pièges classiques

1. **Oublier l'annotation de type à l'utilisation** — un générique (surtout dans une struct) peut demander une annotation explicite ; le compilateur l'indique.
2. **Appeler une méthode sur un générique sans trait bound** — comparer avec `>` ou afficher avec `{}` exige `PartialOrd` / `Display` : le compilateur refuse, il faut ajouter la contrainte.
3. **Renverser un élément d'un `&[T]` sans `Copy`** — on veut renvoyer `list[0]` par valeur alors que `T` n'est ni `Copy` ni `Clone` ; il faut restreindre avec un bound ou lire par référence.
4. **Violer la orphan rule** — implémenter un trait de la bibliothèque standard sur un type de la bibliothèque standard ; ce n'est autorisé que si le trait ou le type est à nous.
5. **Retourner une référence vers une variable locale** — c'est une dangling reference : la variable meurt à la fin de la fonction, le compilateur la refuse à juste titre.
6. **Mettre des lifetimes « au hasard »** — quand la signature n'a qu'une référence en entrée, l'élision suffit ; les annotations en trop embrouillent sans rien garantir.
7. **Coller `'static` partout** — on ne doit l'exiger que si la donnée vit réellement pour toute la durée du programme, sinon on impose une contrainte inutile.
8. **Croire que les annotations allongent la vie des données** — elles ne font que la *décrire* ; une référence retournée doit être **réellement** valide.
9. **Renvoyer `impl Trait` en pensant renvoyer des types différents** — le retour `impl Trait` impose un **seul** type concret, même si plusieurs types implémentent le trait.

## Résumé

1. **Les génériques** (`<T>`) suppriment la duplication : une seule version de fonction/struct/enum pour plusieurs types.
2. **La monomorphisation** rend ceci gratuit : le code est compilé en types concrets, aucune pénalité à l'exécution.
3. **Un trait** définit un comportement (`trait Summary { ... }`) ; on l'implémente avec `impl Trait for Type`, avec ou sans corps par défaut.
4. **La orphan rule** : impossible d'implémenter un trait externe sur un type externe.
5. **Un trait bound** (`T: PartialOrd + Copy`, clause `where`) autorise le compilateur à laisser appeler les méthodes du trait sur un générique.
6. **`impl Trait`** en paramètre ou en retour simplifie la signature, mais le retour impose un seul type concret.
7. **Les lifetimes** (`'a`) décrivent la durée de validité des références et servent au **borrow checker** pour empêcher les dangling references.
8. **Les règles d'élision** (3 règles) infèrent les lifetimes automatiquement ; une signature à plusieurs références demande une annotation.
9. **`'static`** = toute la durée du programme (chaînes littérales) ; à n'utiliser que si la donnée vit vraiment pour toujours.
10. **Génériques + traits + lifetimes se combinent** : `fn plus_long<'a, T>(...) -> ... where T: Display` — le compilateur vérifie à la fois le type, les capacités et la validité.
